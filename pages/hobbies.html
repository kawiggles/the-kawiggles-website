yamato/uss-monitor

yamato and uss-monitor are my daily driver desktop computer and laptop, respectively. uss-monitor is a simple HP laptop I used during my time in college, where I only ever used computers to read and write about philosophy. yamato was the first computer I built, its construction motivated by a desire to record music on a machine with superior processing power to a laptop. Because it's easy to power down the desktop and swap out parts, it is by far my most modified machine. It currently includes a Ryzen 9 7950x, an Nvidia RTX 4080 Super, an Nvidia GTX 1050 Ti, and 32 GB of RAM. The desktop introduced me to video games, a genre of media I have recently become fascinated with. The biggest change I've made to both devices in recent history is switching out the operating systems of each. Before February 2026, both devices ran Windows 11, it being the default option for most PC systems. However, I became frustrated with Windows's tendency to hide information about the system, restrict user freedom, and operate in tension with Linux systems. Motivated by these factors, in addition to my growing desire to use an operating system better suited towards studying for the CompTia Linux+ exam, I made the decision to switch both machines over the the Arch Linux operating system. The process was incredibly rewarding and informative. Both computers currently use the hyprland window manager alongside a neovim plugin stack for development and daily use (Proton has made gaming on Linux much simpler). Linux's incredible ability for customizability in concert with my server has allowed me to build an incredibly efficient productive system where the terminal is my primary means of interacting with the system.

great-eastern

great-eastern is the main server machine on my network. It functions as a network attached storage device for the rest of my machines and as a platform for hosting containerized services, inlcuding Jellyfin, NextCloud, and Trilium Notes. I originally built the computer only to satisfy the obsession I had gained for working with computer hardware; at the time I had no intention of converting the computer into a full homelab. However, as I became invested in the project, I realized that there existed great utility in owning a mass storage device that could double as a server for docker containers. Over the course of several months in 2025, I scavenged eBay and facebook marketplace for cheap storage drives to use in the project. During this time, I also became acquainted with the OS that the server is currently using: Unraid. Unraid is a proprietary evolution of the Slackware Linux distribution. It is unique in that it allows for storage drives of different sizes to be arranged as a parity protected array in a simulacrum of a typical RAID storage setup. A parity drive has its bits set to the product of the XOR operation applied to the associated bit of every other drive in the array. This way, if one drive fails, it can be reconstructed using the rest of the array and the parity drive, offering data protection. Such a setup ensured that I could fully localized the various digital services I used daily, meaning that I would have full control over their functionality and data. I acquired the parts from a wide variety of sources. I purchased an old intel core i5 8600k, motherboard, and RAM from my friend Nathan. An Arc A380 GPU assists with media transcodes. I use an LSI 9211-8i flashed to IT mode as an HBA card for all of the storage drives (enabling Unraid's drive array functionality). I used tailscale to implement a mesh network for my personal devices in order to better secure the server while still enabiling access to the network from any location with internet. A few of my services (like this website) remain exposed to the internet through this domain name. I use nginx to handle port forwarding and to insure that server traffic is limited to interactions with deployed containers. I use ufw and Fail2Ban to provide additional security. This project really was the catalyst that lead to my interest in computer systems as a whole, and continues to inform my education and technical development to this day.

whydah-gally

whydah-gally is a headless machine used for ripping, transcoding, and organizing media. The machine is built from the remnants of an old Optiplex 990 workstation, with additions of an SSD for storage, an Nvidia T400 for hardware accelerated transcoding, and two r/w optical drives. It runs the minimal installation of Ubuntu Server to maximize the potential of its limited processing power. whydah-gally is mostly used to run software like handbrake and ytdlp, but it also doubles as a secondary storage device for my network, running cron jobs to backup important data from my NAS. This way I'll still have a way to restore things like my Trilium notes if great-eastern ever suffers multiple simultaneous hard-drive failures. More recently I've been using the machine to host a Windows VM, with the intention of running a C# language server, practicing implementing virtual machines, and for familiarizing myself with the IT tools available on Windows.

The C Data Structures Project

When first learning C, it quickly became evident to me that a proper understanding of the usage and construction of various data structures and algorithms was necessary in order to succeed in writing software. My data structures and algorithms project is my way of practicing implementing these various data structures and algorithms in a way that simultaneously allows me to practice my memory management, user input handling, systems architeture, and ability to develop a large codebase. The project is a command-line-esque program which parses user commands to construct, manipulate, and deploy various data structures. The project is divided into a central management file and files for each kind of data structure. The management function parses and executes the user commands by getting input from the looping main function and converting it into values using strtok. Those values are then used as arguments for the various operations defined by the program. The management loop also builds and maintains a linked list of "OpenStructs". OpenStructs are nodes which contain pointers to the heads of the various data structures, as well as information about the data structures. Managing memory becomes easy with this method, as memory cleanup simply involves iterating through the loop and calling that nodes associated "destory" function to free the data in the structure as well as the structure itself, before finally freeing the node. The structure also makes identifying and manipulating individual structures easy by simply iterating though the linked list looking for the associated ID. This lookup could be more efficient with an alternate management data structure, such as a hash table, but O(n) time is not awful when it's purely for looking up singluar data structures, and the easy of memory management makes it worth it. This project can be found on my github page as Data-Structures-and-Algorithms.

The C++ Game Engine Project

This project has been my main software project as well as my method for learning C++. The program is the logical outline for a game engine that should theoretically be portable to any graphics engine. The game is a variant of chess, where players take turns moving pieces against an AI opponent. The board is defined as a vector of tile objects, which have (x, y) coordinate values and terrain values. The Tile object is polymorphic, allowing for various piece characteristic modifying functions to be modified depending on terrain type using the same function name. The terrain type for a piece is determined by a perlin noise map, which comes from a headless library by Ryo Suzuki, which is the only external code in the entire project. The project uses several C++ specific tools, such as smart pointers, std library data structures, and lambda functions. It can be found on my github page as Game-Idea-Engine.
